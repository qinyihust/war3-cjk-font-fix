# 根因与补丁设计

以下地址、字段和行为对应兼容表中的精确 DLL。函数名为分析标签，不是官方调试符号。该文件相关 RVA 恰好等于文件偏移；其他 PE 文件通常不成立。

## 1. 字形分配失败导致测宽和绘制失配

字体使用 8 张 256 × 256 的纹理缓存。字号增大时，每张纹理可容纳的汉字减少。`Game.dll + 0x7C5870` 的获取路径在缓存满后淘汰一个旧字，再尝试插入新字。如果新字更宽，释放的空间仍然不足，原路径会直接返回失败。

测宽或换行因这次失败漏算该字，稍后的绘制再次分配却可能成功，于是测量宽度与显示宽度不一致。补丁在 `0x7C5A49` 令插入失败继续沿引擎已有的淘汰路径重试；没有可淘汰的字形时仍然返回失败，保留终止条件。

## 2. UTF-8 游标在接受字符前推进

模式 0 的换行路径 `0x7C65C0` 在超宽判断之前推进输入游标，返回的前缀字节数包含了本行不应接纳的字符。

5 处修改令普通字符只在被接受后推进，同时保留颜色码、换行和极窄行首字符的进度保证。未修改模式变量。历史测量中，可用宽度 819 像素的中文样本，原版前缀实际为 840 像素；修正后为 810 像素。ASCII 样本也有同类问题。

## 3. 批量文字遗漏纹理失效处理

第一版长局仍出现“物品栏”串字。其原始 UTF-8 正确，字符串 `+0x80` 的纹理失效标志已设置，但批量路径继续使用旧几何/纹理坐标；单字符串路径具有相应检查。

在 `0x7C6333` 的批量渲染调用前，新增短代码遍历批次中的字符串，对失效项调用引擎自己的 `0x7C7110` 几何重建，然后继续原 `0x7C5EB0` 渲染路径。清除失效标志发生在重建之前，因此重建期间再发生的失效不会被覆盖，后续绘制仍可重试。

## 4. 重新分配后未上传像素，透明区留下旧笔画

CPU 字形位图已上传过时，其描述符 `+0x24` 为 0。GPU 字形被淘汰并分配到新槽位后，纹理重建代码仍按这个 CPU 状态跳过拷贝。实际取证中，“栏”的 CPU 位图正确，新槽位却保留了“群”的像素。

![CPU glyph versus stale atlas slot](images/glyph-atlas-evidence.png)

图为故障诊断：左侧为正确源位图，右侧橙框为错误目标像素。它不是补丁成功截图。

仅重新复制非透明像素还会留下旧字笔画。第二版在脏纹理更新时先清零整张 256 × 256 × 4 字节缓冲区，再复制其中所有有效字形，取消 CPU 已上传标志导致的跳过。纹理未变脏时沿原快速路径运行。

## 修改位置

| 位置 | 补丁定义 ID | 作用 |
|---|---|---|
| `0x7C5A49` | `glyph-allocation-retry` | 继续淘汰直到插入成功或无字可淘汰 |
| `0x7C6714` | `utf8-defer-advance` | 取消提前推进 |
| `0x7C676A` | `utf8-control-sequence` | 保留控制序列消费 |
| `0x7C681F` | `utf8-accepted-character` | 接受字符后推进 |
| `0x7C6835` | `utf8-newline-advance` | 保留换行推进 |
| `0x7C6847` | `utf8-narrow-line-progress` | 保留极窄行进度 |
| `0x86C400` | `batch-rebuild-stub` | 失效批量字符串重建，54 字节 |
| `0x86C440` | `atlas-clear-stub` | 脏纹理清零，33 字节 |
| `0x7C6333` | `batch-rebuild-hook` | 调用批量字符串前处理 |
| `0x7C1AD1` | `atlas-clear-hook` | 进入纹理清零短代码 |
| `0x7C1B3B` | `atlas-copy-live-glyphs` | 重建所有有效字形像素 |

两段代码使用代码节末尾现有映射页的空白区域，分支为相对寻址，不增加 PE 节、DLL 或重定位。具体字节以 [版本定义](../patches/war3-1.25.1.6397.json) 为准。原生测试验证空链表、选择性重建、重建期间再次失效、寄存器/栈/进位标志，以及纹理清零范围两侧保护区。

## 安装器结构

上述地址表描述已经完成长局的 1.25b。2.1.0 的共用生成器将同一逻辑用于 8 个精确构建：1.20e / 1.21 使用保留帧指针的编译布局，1.22～1.26 使用另一种布局。两类的字符串失效位、批次链表及图集数据结构经核对一致；旧版图集原指令写入 ESI，新版写入 ECX，生成代码分别保留对应输出。旧版使用内联清零，新版调用现有 `memset`。

1.21 / 1.24e 的 `.text` 尾部仅余 48 / 70 字节，不足以容纳两段代码。它们新增 128 字节虚拟内容、4 KiB 原始数据的 `.cjk` 只读可执行节，原文件及尾部覆盖数据保留。1.21 原文件并未按页结束，因此加上对齐共增长 8,132 字节；1.24e 增长 4,096 字节。所有跳转采用相对寻址，不新增绝对地址重定位。恢复时先验证完整已知指纹，逆向修改头部并截去新增内容，再验证原版完整哈希。

各版本地址与字节以 `tools/engine-layouts.json` 和 `patches/` 为准。共用生成器不意味着支持未经验证的任意 DLL；实际安装仍只按内嵌完整指纹选择数据。

- `PatchProfile`：验证内嵌定义，限制指纹、修订号、长度、编辑边界、重叠和备份文件名。
- `PatchEngine`：纯内存变换，已知旧版本先恢复原版，再生成当前版本；每一阶段都核对完整哈希。
- `PatchService`：游戏退出检查、同目录操作互斥、原版备份、同卷暂存、写入刷新、替换前目标复核、原子替换及最终校验。
- `Program` / `MainForm`：CLI 与图形界面；不负责决定修改偏移。

互斥锁保护同一 Windows 会话中指向同一规范化路径的安装器操作，不声称能够阻止任意第三方进程同时写文件。替换前还会重新检查游戏进程和目标哈希；检测到外部修改时保留外部文件并停止替换。

窗口变化会触发字体尺寸及缓存重建，这与切换窗口后暂时恢复的现象一致。但窗口重建并不修正上述路径；本次长局没有使用窗口切换作为验证捷径。

清空和完整填充增加脏纹理重建时的工作量，尚无原版与补丁的帧率基准对照。参见 [验证范围](VALIDATION.md) 和 [外部参考来源](../NOTICE.md)。
